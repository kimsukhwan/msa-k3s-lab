①

빌드·의존성 관리 (Gradle 생태계)

Gradle 빌드 도구

코드를 컴파일하고, 테스트를 돌리고, 실행 가능한 jar를 만들어주는 빌드 자동화 도구. build.gradle.kts(Kotlin DSL로 쓴 설정 파일)에 "무엇을 어떻게 빌드할지"를 적어두면 ./gradlew 명령으로 그대로 실행된다.

Gradle Wrapper (gradlew)

내 컴퓨터에 Gradle이 설치돼 있지 않아도 프로젝트가 지정한 버전의 Gradle을 자동으로 내려받아 실행해주는 스크립트. gradle/wrapper/gradle-wrapper.properties에 버전이 적혀 있다 — 팀원마다 Gradle 버전이 달라서 생기는 "내 컴퓨터에선 되는데" 문제를 없애준다.

멀티모듈(Multi-module) 프로젝트

한 저장소 안에 :api, :batch처럼 서로 다른 실행 단위(모듈)를 두는 구조. settings.gradle.kts의 include(...)로 모듈을 등록한다. 각 모듈은 독립적으로 빌드/배포되지만 공통 설정은 루트 build.gradle.kts에서 나눠 쓸 수 있다.

JaCoCo (Java Code Coverage)

테스트가 실제 코드를 얼마나 "실행해봤는지"(커버리지)를 측정하는 도구. 예를 들어 100줄짜리 함수 중 80줄이 테스트 중에 실행됐다면 커버리지 80%. 이 프로젝트는 0.80(80%) 이상을 통과 기준으로 두고, 기준 미달이면 ./gradlew bootJar 빌드 자체가 실패하도록 게이트를 걸어둔다 — "테스트를 아예 안 쓰고 넘어가는 것"을 막기 위함이다.

주의: 커버리지가 높다고 테스트 품질이 좋다는 뜻은 아니다 — "실행은 됐지만 검증(assert)은 부실한" 테스트로도 숫자를 채울 수 있다. 그래서 최소 기준일 뿐, 목표가 아니다.

QueryDSL

SQL을 문자열로 직접 안 쓰고, 타입이 보장되는 Kotlin/Java 코드로 쿼리를 작성하게 해주는 라이브러리. 엔티티마다 QXxx라는 이름의 "Q클래스"를 자동 생성해서 그걸로 조건을 조립한다(예: QCmu001Tm.cmu001Tm.usrid.eq(id)). 오타로 인한 런타임 SQL 에러를 컴파일 시점에 잡아준다.

KSP (Kotlin Symbol Processing)

QueryDSL의 Q클래스처럼, 코드를 분석해서 또 다른 코드를 자동 생성해주는 Kotlin 컴파일러 플러그인 방식. gradle.properties의 ksp.incremental=false는 KSP의 증분 빌드(바뀐 부분만 다시 생성)가 간헐적으로 깨지는 문제를 피하려고 끈 설정이다.

io.spring.dependency-management 플러그인

Spring Boot가 검증해둔 라이브러리 버전 조합(BOM)을 그대로 가져다 쓰게 해주는 플러그인. 이게 있으면 implementation("org.springframework.boot:spring-boot-starter-web")처럼 버전 번호 없이 의존성을 선언해도 Spring Boot 버전에 맞는 호환 버전이 자동으로 선택된다.

②

테스트

@WebMvcTest

애플리케이션 전체를 안 띄우고 컨트롤러 계층만 가볍게 띄워서 테스트하는 Spring Boot 어노테이션. 실제 DB 연결 없이, 컨트롤러가 "요청 파라미터를 제대로 받는지" · "URL 매핑이 맞는지" 같은 걸 빠르게 검증할 때 쓴다. 프로젝트 규칙상 쿼리파라미터 바인딩, Spring Data 파생쿼리, SpEL 캐시 키처럼 컴파일로는 못 잡고 런타임에만 깨지는 부분은 반드시 이 테스트로 고정해야 한다.

MockMvc

@WebMvcTest 안에서 실제 HTTP 요청처럼 컨트롤러를 호출해보는 도구. mockMvc.perform(get("/loan/applications")).andExpect(status().isOk())처럼 써서 "진짜 요청을 보내면 어떻게 반응하는가"를 검증한다.

슬라이스 테스트 (Slice Test)

애플리케이션 전체(모든 Bean)를 띄우는 대신, 딱 필요한 계층(예: 컨트롤러만, 혹은 JPA Repository만)만 잘라서(slice) 띄우는 테스트 방식. @WebMvcTest가 대표적인 슬라이스 테스트다. 전체를 다 띄우는 것보다 훨씬 빠르다.

③

웹·API 계층

DTO (Data Transfer Object)

계층과 계층 사이(혹은 서비스와 서비스 사이)에서 데이터를 실어 나르는 전용 객체. 엔티티(DB 테이블과 1:1)를 API 응답으로 그대로 내보내지 않고 DTO로 한 번 감싸는 이유는, DB 구조가 바뀌어도 API 계약(응답 모양)은 그대로 유지하기 위해서다.

MDC (Mapped Diagnostic Context)

로그 한 줄 한 줄에 "이 요청이 누구의 것인지"를 자동으로 끼워 넣는 SLF4J/Logback 기능. MDC.put("requestId", "...")로 값을 넣어두면, 그 뒤에 찍히는 모든 로그에 requestId가 자동으로 붙는다. msa-k3s-lab 랩에서 만든 CorrelationFilter가 actionId/requestId를 MDC에 넣는 방식이 정확히 이 패턴이다 — 그래야 여러 서비스에 흩어진 로그를 한 번에 묶어서 찾을 수 있다.

Filter vs Interceptor

둘 다 "요청이 컨트롤러에 도달하기 전/후에 가로채는" 역할을 하지만 계층이 다르다. Filter(Servlet 표준)는 Spring보다 더 바깥쪽, 요청이 서블릿 컨테이너에 들어오자마자 실행된다. Interceptor(Spring 고유)는 Spring이 요청을 처리하는 안쪽 단계에서 실행되며 컨트롤러 정보에 접근할 수 있다. 로그인 인증 체크, 요청 시간 측정, MDC 세팅처럼 "모든 요청에 공통으로 걸어야 하는 일"에 주로 쓴다.

CORS (Cross-Origin Resource Sharing)

브라우저가 "지금 이 페이지와 다른 출처(도메인·포트)의 서버"에 요청을 보낼 때 걸리는 보안 제한. 예를 들어 localhost:5173에서 실행 중인 React 앱이 localhost:8888 API를 부르면 브라우저가 기본적으로 막는다 — 서버가 응답 헤더에 Access-Control-Allow-Origin을 명시해줘야 브라우저가 허용한다.

RestClient

Spring 6.1부터 들어온 동기식(blocking) HTTP 클라이언트. 예전의 RestTemplate을 대체하는 최신 방식으로, 다른 서비스를 호출할 때(port-out 어댑터 구현체 등) 쓴다. RestClient.builder().baseUrl(...).requestInterceptor(...)처럼 체이닝으로 설정한다.

Actuator / Micrometer

Actuator는 Spring Boot 앱의 상태(헬스체크, 지표 등)를 /actuator/* 엔드포인트로 노출해주는 모듈. Micrometer는 그 지표를 실제로 수집·집계하는 라이브러리로, micrometer-registry-prometheus를 추가하면 /actuator/prometheus에서 Prometheus가 읽을 수 있는 형식으로 지표가 나온다.

ApiResponse / envelope

모든 API 응답을 { "responseCode": 0, "responseMessage": "SUCCESS", "data": {...} } 같은 공통 틀(envelope)로 감싸는 방식. 호출하는 쪽(프론트/다른 서비스)이 매번 다른 응답 모양을 예측할 필요 없이 한 가지 파싱 로직만 두면 되게 해준다.

④

데이터베이스

HikariCP

DB 커넥션 풀(connection pool) 라이브러리. 매 요청마다 새 DB 연결을 맺고 끊으면 느리므로, 미리 연결을 여러 개 만들어두고 재사용한다. Spring Boot가 기본으로 내장하고 있어 별도 설정 없이도 동작한다.

JPA / Hibernate / ddl-auto

JPA는 "객체를 DB 테이블에 자동으로 매핑해주는" 자바 표준 명세이고, Hibernate는 그 명세의 실제 구현체다. spring.jpa.hibernate.ddl-auto: validate는 "애플리케이션이 시작될 때 엔티티와 실제 DB 테이블 구조가 일치하는지만 검사하고, 절대 테이블을 만들거나 바꾸지 않는다"는 뜻 — 스키마는 DBA가 관리하고 코드는 그걸 따라가기만 한다는 이 프로젝트 정책과 맞닿아 있다.

Flyway 이 프로젝트는 미사용

DB 스키마 변경 이력을 V1__xxx.sql 같은 버전 파일로 관리해 자동 적용해주는 마이그레이션 도구. 예전에는 이 저장소도 썼지만, "파일은 있는데 실제 DB엔 적용이 안 됨" 같은 드리프트가 반복돼 2026-07-21부로 전면 폐기했다. 지금은 spring.flyway.enabled: false이고, 코드베이스에 .sql 마이그레이션 파일 자체를 두지 않는다.

ExternalName Service

쿠버네티스 Service 타입 중 하나로, "이 이름으로 부르면 실제로는 클러스터 밖의 특정 주소로 보내라"는 DNS 별칭 역할을 한다. 이 프로젝트에서는 외부 PostgreSQL(`thenext`)을 bank-postgres라는 ExternalName으로 감싸서, 코드는 항상 bank-postgres라는 이름만 알면 되고 실제 IP가 바뀌어도 코드를 안 고쳐도 되게 한다.

CoreDNS

쿠버네티스 클러스터 안에서 "서비스 이름 → 실제 주소(ClusterIP 등)"를 자동으로 찾아주는 DNS 서버. Pod가 loan-service라는 이름만 알면 CoreDNS가 실제 위치로 변환해준다 — IP를 몰라도 서로를 찾을 수 있는 이유가 이것이다.

Patroni / etcd / HAProxy (PostgreSQL HA)

PostgreSQL을 여러 대(Primary + Replica)로 이중화해서 장애에 대비하는 구성 요소들. Patroni가 어느 노드가 Primary인지 관리하고, etcd는 그 상태를 저장하는 분산 키-값 저장소, HAProxy는 클라이언트 요청을 항상 현재 Primary로 보내주는 로드밸런서다. Primary가 장애나면 Patroni가 자동으로 Replica 하나를 새 Primary로 승격시킨다.

Keepalived / VIP (Virtual IP)

VIP는 특정 물리 서버에 고정되지 않고 "지금 살아있는 서버"에 붙는 가상 IP 주소. Keepalived는 여러 서버 중 하나가 죽으면 VIP를 다른 살아있는 서버로 자동으로 옮겨주는 프로그램. PostgreSQL Primary가 장애조치돼도 클라이언트가 바라보는 주소(VIP)는 그대로라 코드 수정이 필요 없다.

⑤

아키텍처 패턴

MSA (Microservices Architecture)

하나의 거대한 애플리케이션(모놀리식) 대신, 도메인별로 독립 배포 가능한 작은 서비스 여러 개로 나누는 아키텍처. 서비스마다 자기 DB를 갖고, 서로 REST/이벤트로 통신한다. 장점은 독립 배포·독립 장애 격리, 단점은 서비스 간 호출·데이터 정합성 관리가 복잡해진다는 것.

port-out 헥사고날에서 빌려온 개념

다른 서비스나 외부 시스템을 호출하는 코드를 interface + 구현체(Adapter)로 분리하는 패턴. interface가 "port"(포트), 실제 HTTP 호출 등을 구현한 클래스가 "adapter"다. 이렇게 분리해두면 나중에 호출 방식이 바뀌어도(REST→gRPC 등) 비즈니스 로직은 안 건드리고 Adapter만 바꾸면 되고, 테스트할 때도 interface를 mock으로 바꿔치기하기 쉽다. 이 프로젝트는 이 개념을 "밖으로 나가는 호출"에만 적용하고 컨트롤러→서비스 방향(port-in)에는 적용하지 않는다 — 그래서 "완전한 헥사고날 아키텍처"는 아니고 "Layered + port-out"이라고 부른다.

헥사고날 아키텍처 (Ports & Adapters)

애플리케이션의 핵심 로직을 중심에 두고, 그 바깥을 전부 "포트(인터페이스)"로 감싸 외부 세계(DB, 웹, 다른 서비스)와의 의존을 역전시키는 아키텍처 스타일. 들어오는 방향(port-in, 예: UseCase 인터페이스)과 나가는 방향(port-out) 둘 다 인터페이스로 감싸는 게 정통 방식이다.

BFF (Backend For Frontend)

특정 클라이언트(웹, 모바일 등) 전용으로 여러 백엔드 서비스의 응답을 조합해주는 중간 계층. 이 프로젝트에서는 web(Next.js)이 이 역할을 한다 — gateway는 인증·라우팅만 하고, "화면에 필요한 형태로 여러 API를 조합"하는 일은 BFF인 web이 담당한다.

DAG (Directed Acyclic Graph, 순환 없는 방향 그래프)

서비스 간 호출 관계를 화살표로 그렸을 때 순환(cycle)이 없는 상태. A→B→A처럼 순환이 생기면 배포 순서를 정할 수 없고 장애가 서로에게 전파된다. 이 프로젝트는 "호출 그래프는 DAG여야 한다"는 원칙 아래, ID→표시명 역조회 때문에 생기던 순환을 전부 없애고 지금은 순환 0개 상태를 유지한다.

⑥

인증·보안

JWT (JSON Web Token)

로그인한 사용자의 정보(누구인지, 권한이 뭔지)를 암호학적으로 서명해서 담아두는 토큰. 서버는 이 토큰에 적힌 서명만 검증하면 되므로 매 요청마다 DB에서 세션을 조회할 필요가 없다(stateless).

JWT 클레임 (iss / aud / exp / jti)

JWT 내용물(payload)에 들어가는 표준 항목들. iss(issuer)는 누가 발급했나, aud(audience)는 누구 쓰라고 발급했나, exp(expiration)는 언제까지 유효한가, jti(JWT ID)는 토큰의 고유 일련번호다. 검증할 때 서명과 함께 이 값들을 확인한다 — 특히 aud 검증은 "같은 발급자가 다른 제휴사용으로 발급한 토큰을 우리한테 재사용하는 공격"을 막고, jti는 폐기 목록(Redis)에 올려 로그아웃 즉시 토큰을 무효화하는 데 쓴다(랩에서 검증, 실서비스 적용 여부는 미확정).

JWKS (JSON Web Key Set)

JWT 서명을 검증하는 데 필요한 공개키들을 모아둔 목록. 슈퍼앱처럼 외부에서 발급한 토큰을 검증할 때, 우리 서버가 슈퍼앱의 JWKS 엔드포인트(/.well-known/jwks.json)를 조회해서 공개키를 캐싱해두고 그걸로 서명을 검증한다. 발급자와 검증자가 다른 조직이어도 되는 이유가 이것이다.

세션 없는 요청 서명 (Stateless Request Signing) 최종 채택 (2026-08-24)

고객(슈퍼앱) 채널 인증의 최종 방식. 채널BFF가 슈퍼앱 토큰을 매 요청 1차 검증하고, 그 요청 하나에 대해 HMAC 서명(공유 비밀 + method·path·timestamp·nonce·custKey)을 생성해 gateway로 보낸다. gateway는 서명·timestamp(±60초)·nonce 중복(짧은 Redis 캐시)만 확인하고 — 세션도, 발급 토큰도, 조회할 상태도 없다. 채택 이유: 슈퍼앱의 로그인·로그아웃을 우리 쪽에서 감지할 방법이 없다는 게 확인되면서, 세션(로그인 상태)을 우리 내부에 유지하려는 시도 자체가 실체 없는 TTL 근사치일 뿐임이 드러났다 — 그래서 세션 개념을 버리고 매 요청을 그 자리에서 독립적으로 증명하는 쪽을 택했다. mTLS(채널 증명)와 HMAC(요청 증명)이 서로 다른 비밀에 의존해 한쪽이 뚫려도 방어가 남는다.

토큰 이중 검증 (1차 채널BFF · 2차 gateway) 이전 검토안 (2026-08-20)

고객 요청의 같은 슈퍼앱 토큰을 채널BFF와 gateway 두 지점에서 검증하려던 초기안. gateway가 슈퍼앱 JWKS(kid)로 직접 2차 검증해야 해서, 내부 인증 경계가 타사(슈퍼앱)의 서명키·키 교체 일정에 의존하게 된다는 문제로 폐기됐다. "세션 없는 요청 서명"으로 최종 결정되기 전 단계.

Token Exchange (토큰 교환) 이전 검토안 (2026-08-21)

채널BFF가 슈퍼앱 토큰을 1차 검증한 뒤 auth-service에서 내부 토큰으로 교환받아 gateway가 우리 키로만 검증하던 중간 단계 방식. 타사 키 의존은 해결했지만, 이후 "슈퍼앱 로그인·로그아웃을 감지할 수 없다"는 제약이 확인되며 — 이 방식이 전제한 "세션(내부 토큰)을 얼마간 유지한다"는 접근 자체가 성립하지 않는다는 게 드러나 폐기됐다. "세션 없는 요청 서명"으로 최종 결정됐다.

HMAC 요청 서명 (Request Signing)

토큰이 아니라 요청 하나하나에 서명을 붙이는 인증 방식. 발신자와 수신자가 공유 비밀(대칭키) 하나를 갖고, 요청의 메서드·경로·시각·난수·주요 파라미터를 합쳐 HMAC 서명을 계산한다. 수신자는 같은 계산을 반복해 값이 일치하는지, timestamp가 유효 창 안인지, nonce가 재사용되지 않았는지를 확인한다. AWS SigV4와 같은 원리. PKI(인증서·개인키 관리)가 필요 없고, 세션이나 발급 서버 없이도 매 요청을 독립적으로 증명할 수 있어 이 프로젝트의 채널 인증 최종안으로 채택됐다.

재전송 공격 (Replay Attack) / nonce

이미 보낸(정상적인) 요청을 그대로 다시 전송해 부정 이용하는 공격. 서명이나 헤더 값 자체가 유출·도청되면, 그 값을 그대로 재사용하는 것만으로 인증을 통과할 수 있어 서명만으로는 막지 못한다. timestamp(유효 시간 창 밖의 요청 거부)와 nonce(요청마다 다른 난수, 한 번 본 값은 짧은 시간 동안 Redis 등에 기록해 재사용 거부)를 함께 써서 막는다. "세션 없는 요청 서명"에서 재전송 방지의 핵심 장치.

custKey / cust_unno

custKey는 슈퍼앱 세계의 고객 식별자 — 고객 토큰에 실려 오는 값이다. cust_unno는 우리 원장(DB)의 내부 고객 고유번호. 두 세계의 식별자가 다르므로 어딘가에서 번역(custKey→cust_unno)이 필요한데, 그 지점을 gateway로 할지 customer-service로 할지는 아직 미확정이다(architecture.drawio 체크리스트 ④). 랩에서는 이 매핑을 fail-closed(매핑 실패 시 요청 거부)로 검증했다.

RBAC (Role-Based Access Control)

사용자에게 직접 권한을 주는 대신 "역할(Role)"을 부여하고, 역할마다 할 수 있는 일을 정의하는 권한 관리 방식. "홍길동"이 아니라 "지점장 역할"에게 권한을 준 뒤 홍길동을 그 역할에 배정하는 식이라, 인사이동이 생겨도 역할 배정만 바꾸면 된다.

HMAC vs RSA (서명 방식)

둘 다 JWT에 서명하는 방식이지만 성격이 다르다. HMAC(예: HS256)은 발급자와 검증자가 같은 비밀키를 공유해야 한다 — 내부 직원 인증(auth-service)처럼 발급·검증을 같은 조직이 다 할 때 적합. RSA(예: RS256)는 발급자가 개인키로 서명하고 검증자는 공개키만 있으면 된다 — 슈퍼앱처럼 발급자와 검증자가 다른 조직일 때 적합(그래서 JWKS로 공개키만 배포한다).

MFA (Multi-Factor Authentication, 다중 인증)

비밀번호(지식) 외에 OTP·인증 앱처럼 다른 종류의 인증 수단을 하나 더 요구하는 방식. 비밀번호만 뚫려도 로그인을 못 하게 막아준다.

⑦

쿠버네티스 기본 오브젝트

Pod

쿠버네티스에서 배포할 수 있는 가장 작은 단위. 컨테이너 하나(또는 밀접하게 관련된 여러 개)를 감싼다. Pod는 언제든 죽고 새로 만들어질 수 있는 "일회용" 존재라, Pod 자체의 IP나 이름에 의존하면 안 된다(그래서 Service가 필요하다).

Deployment

"이 이미지로 Pod를 몇 개 유지해라"를 선언하는 오브젝트. 실제로 Pod를 만들고 개수를 유지하는 건 Deployment가 자동 생성하는 ReplicaSet이 한다. 이미지 태그를 바꾸고 다시 적용하면 Deployment가 알아서 롤링 업데이트(하나씩 순차 교체)한다.

ReplicaSet

"Pod가 N개 유지되도록 감시"하는 컨트롤러. Pod 하나가 죽으면 즉시 새로 만들어서 개수를 맞춘다. 보통 Deployment가 자동으로 만들어주므로 직접 다룰 일은 거의 없다.

Service

여러 개(혹은 매번 바뀌는) Pod를 하나의 고정된 이름과 주소로 묶어주는 오브젝트. product-service라는 Service 이름으로 호출하면, 그 뒤에 있는 Pod가 몇 개든, IP가 바뀌든 상관없이 그중 하나로 요청이 전달된다(로드밸런싱).

Namespace

하나의 클러스터 안을 논리적으로 나누는 구획. bank-dev 같은 이름공간 안에 그 환경의 리소스를 모아둔다. 같은 이름의 리소스라도 Namespace가 다르면 별개로 취급된다.

ConfigMap / Secret

둘 다 설정값을 코드 밖에 분리해서 Pod에 주입하는 방법. ConfigMap은 민감하지 않은 값(DB_HOST 등), Secret은 민감한 값(비밀번호, 토큰 등 — base64로 인코딩되지만 암호화는 아니므로 접근 권한 관리가 중요하다)에 쓴다. 이 프로젝트 정책상 모든 비밀값은 반드시 Secret으로만 주입하고 코드에 fallback 기본값을 두지 않는다.

kubeadm

쿠버네티스 클러스터를 직접(수동으로) 구축할 때 쓰는 표준 도구. k3s처럼 이미 다 갖춰진 경량 배포판과 달리, CNI·스토리지 등을 하나하나 따로 골라 설치해야 하는 대신 클라우드 벤더에 종속되지 않는 "표준" 쿠버네티스를 만들 수 있다. 이 프로젝트는 k3s가 아니라 kubeadm 기반 클러스터를 쓴다.

containerd

실제로 컨테이너를 실행하는 저수준 런타임. Docker도 내부적으로 비슷한 역할의 컴포넌트를 쓰는데, 쿠버네티스는 Docker 없이 containerd만으로 컨테이너를 직접 실행한다(더 가볍고, 쿠버네티스 전용 인터페이스인 CRI를 따른다).

Readiness Probe / Liveness Probe

Readiness Probe는 "이 Pod가 지금 트래픽을 받을 준비가 됐는가"를 주기적으로 확인 — 준비 안 됐으면 Service가 트래픽을 안 보낸다. Liveness Probe는 "이 Pod가 아직 살아있는가"를 확인 — 응답이 없으면 쿠버네티스가 그 Pod를 강제로 재시작한다. 앱을 처음 띄울 때 준비되는 데 시간이 걸리면 initialDelaySeconds로 유예 시간을 준다.

HPA (Horizontal Pod Autoscaler)

CPU 사용률 등의 지표를 보고 Pod 개수를 자동으로 늘리거나 줄여주는 기능. 온프레미스 kubeadm 클러스터는 클라우드처럼 노드 자체를 자동으로 늘려주진 않으므로(오토스케일 아님), 정해진 노드 안에서 Pod 개수만 조절하는 정도로 이해하면 된다.

PodDisruptionBudget (PDB)

노드 점검·업그레이드처럼 계획된 작업으로 Pod들을 한꺼번에 내릴 때, "최소 이 정도는 항상 떠 있어야 한다"는 하한선을 정해두는 오브젝트. 이게 없으면 배포본의 Pod가 replica 3개인데 점검 중에 3개가 동시에 내려가 서비스가 완전히 끊길 수 있다.

⑧

쿠버네티스 네트워킹

CNI (Container Network Interface) / Calico

CNI는 "Pod들이 서로 통신할 수 있게 네트워크를 구성하는" 표준 규격. kubeadm은 이 부분을 직접 골라 설치해야 하는데, 이 프로젝트는 Calico라는 CNI 구현체를 쓴다.

Ingress 이 프로젝트는 Gateway API로 전환

클러스터 밖에서 들어오는 HTTP 요청을 Host/Path 규칙에 따라 알맞은 Service로 라우팅해주는 전통적인 방식. 쿠버네티스 커뮤니티가 "유지보수 모드"로 전환하고 후속 표준으로 Gateway API를 밀고 있어, 이 프로젝트는 Ingress 대신 Gateway API를 채택했다.

Gateway API (GatewayClass / Gateway / HTTPRoute)

Ingress의 후속 표준. 역할이 셋으로 분리된다 — GatewayClass는 "어떤 컨트롤러 구현체를 쓸지" 선언, Gateway는 그 구현체의 실제 진입점(리스너·포트), HTTPRoute는 서비스별 라우팅 규칙(예전 Ingress가 혼자 하던 일). 역할이 나뉘어 있어 인프라 담당자와 서비스 담당자가 서로의 영역을 안 건드리고 관리할 수 있다.

Envoy Gateway

Gateway API 표준을 구현한 실제 소프트웨어(컨트롤러) 중 하나. 이 프로젝트가 채택한 구현체로, Envoy 프록시를 기반으로 동작한다. 주의: k8s API의 Gateway kind(오브젝트 이름)와, 이 프로젝트 자체 애플리케이션인 gateway-service는 이름이 같아 보이지만 완전히 다른 것이다 — 사람 사이에서는 항상 "Envoy Gateway"라고 풀어 불러서 헷갈림을 없앤다.

ClusterIP / NodePort / LoadBalancer (Service 타입)

Service를 어디까지 노출할지 정하는 타입. ClusterIP(기본값)는 클러스터 내부에서만 접근 가능. NodePort는 모든 노드의 특정 포트로 외부에서 접근 가능하게 열어준다. LoadBalancer는 클라우드가 실제 외부 IP를 발급해주는 타입(온프레미스에선 MetalLB 같은 별도 도구가 필요).

kube-vip

클라우드 로드밸런서 없이도 특정 서비스에 가상 IP(VIP)를 붙여주는 온프레미스용 도구. 이 프로젝트에서는 API 서버(Master 노드들) 앞단 VIP의 구현 방식으로 결정됐다 — Master 3대 중 리더 1대가 자기 NIC에 VIP를 달고, 리더가 죽으면 다른 Master가 이어받아 접속 주소가 유지된다. L4 대신 이걸 택한 이유는 클러스터 제어 경로가 외부 장비에 의존하지 않게 하기 위해서다.

⑨

스토리지

PV / PVC (PersistentVolume / PersistentVolumeClaim)

Pod는 언제든 사라졌다 새로 생기는 존재라, Pod 안에 저장한 파일도 같이 사라진다. PV는 "실제로 존재하는 저장 공간"(디스크·NFS 등), PVC는 애플리케이션이 "이만큼의 저장 공간이 필요하다"고 요청하는 것. PVC가 PV에 연결(바인딩)되면 Pod가 재시작해도 데이터가 유지된다.

StorageClass

PVC가 요청됐을 때 "어떤 방식으로 PV를 자동으로 만들지"를 정의해둔 템플릿. 예를 들어 nfs-client-file StorageClass는 PVC가 생성될 때마다 NFS 서버에 하위 폴더를 자동으로 파주는 provisioner를 가리킨다.

NFS (Network File System)

네트워크로 공유하는 파일 저장소. 여러 Pod(심지어 여러 노드에 흩어진 Pod들)가 같은 파일을 동시에 읽고 쓸 수 있다는 게 특징이라, 로컬 디스크와 달리 "여러 서비스가 공유해야 하는 파일"에 적합하다. 단, Kafka처럼 아주 잦은 파일 잠금이 필요한 워크로드에는 안 맞아서 로컬 디스크를 권장한다.

emptyDir

PVC 없이 그냥 Pod가 살아있는 동안만 유지되는 임시 저장 공간. Pod가 사라지면 데이터도 같이 사라진다. msa-k3s-lab 랩에서 Mimir·Prometheus agent처럼 "데이터가 없어져도 큰 문제 없는" 컴포넌트에 간단히 이걸 썼다.

⑩

CI/CD · GitOps

CI (Continuous Integration) vs CD (Continuous Deployment)

CI는 코드를 push할 때마다 자동으로 빌드·테스트하는 것. CD는 그 결과물을 자동으로 실제 서버(클러스터)에 배포하는 것. CI는 비교적 쉽게 자동화되지만, CD는 "누가 클러스터에 접근할 수 있는가"의 문제가 있어 GitOps(ArgoCD 등) 같은 별도 장치가 필요할 때가 많다.

GitHub Actions (workflow / job / step)

GitHub에 내장된 CI/CD 자동화 도구. .github/workflows/*.yaml 파일 하나가 workflow 하나이고, 그 안에 여러 job(병렬 또는 순차로 도는 단위)이 있고, job은 여러 step(순서대로 실행되는 명령)으로 구성된다.

GHCR (GitHub Container Registry, ghcr.io)

GitHub이 제공하는 Docker 이미지 저장소. GitHub Actions는 매 실행마다 자동 발급되는 GITHUB_TOKEN으로 여기에 로그인할 수 있어서, 사람이 별도로 비밀번호나 PAT을 등록할 필요가 없다.

GitOps

"git 저장소에 적힌 내용이 곧 클러스터가 가져야 할 정답 상태"라고 정하고, 그 둘을 자동으로 일치시키는 운영 방식. 사람이 kubectl apply를 직접 치는 대신, 클러스터 안의 에이전트(ArgoCD 등)가 git을 계속 지켜보다가 달라지면 스스로 동기화한다. "누가 언제 무엇을 배포했는지"가 전부 git 커밋 이력에 남는다는 장점이 있다.

ArgoCD

쿠버네티스 클러스터 안에서 도는 GitOps 도구. git 저장소의 특정 경로(예: k8s/)를 감시하다가, 내용이 바뀌면 자동으로 kubectl apply에 해당하는 일을 대신 해준다. Application이라는 오브젝트로 "어느 저장소의 어느 경로를, 어느 클러스터의 어느 namespace에 반영할지"를 등록한다. 자체 웹 대시보드에서 Sync 상태(Synced/OutOfSync)와 Health 상태(Healthy/Progressing/Degraded)를 실시간으로 볼 수 있다.

Sync / Health 상태 (ArgoCD)

Sync 상태는 "git에 적힌 내용과 클러스터의 실제 상태가 같은가"(Synced=같음, OutOfSync=다름). Health 상태는 "그 리소스가 실제로 잘 동작하고 있는가"(Healthy=정상, Progressing=배포 중, Degraded=문제 있음). 이 둘은 별개다 — git과 클러스터가 일치해도(Synced), 그 배포 자체가 실패해서 Pod가 안 뜨면 Degraded일 수 있다.

이미지 태그를 커밋 SHA로 bump하는 이유

ArgoCD는 git의 "텍스트"만 비교한다. 매니페스트에 항상 image: xxx:latest라고만 적혀 있으면, 실제 이미지 내용이 바뀌어도 git 쪽 텍스트는 그대로라 ArgoCD 입장에서는 "바뀐 게 없다." 그래서 CI가 이미지를 push한 뒤 매니페스트의 태그를 그 커밋의 SHA(예: 24656ec02d...)로 고쳐 쓰고 다시 git에 커밋한다 — 그래야 ArgoCD가 "spec이 바뀌었다"고 인식해서 동기화한다.

멀티아키텍처 빌드 (buildx / QEMU)

같은 이미지 태그 하나가 amd64(인텔/AMD 서버, GitHub Actions 러너 등)와 arm64(Apple Silicon 맥 등)에서 둘 다 동작하도록 빌드하는 것. Docker의 buildx가 여러 아키텍처를 빌드하는 기능을 제공하고, QEMU(에뮬레이터)가 amd64 러너 안에서 arm64 코드를 흉내내 빌드할 수 있게 해준다. 이게 안 맞으면 no match for platform in manifest 에러로 이미지를 못 당겨온다.

imagePullPolicy

Pod를 만들 때 이미지를 언제 다시 받아올지 정하는 옵션. Always는 매번 레지스트리에서 새로 받아온다(태그가 재사용될 때 필수). IfNotPresent는 노드에 이미 있으면 그걸 그대로 쓴다(로컬 개발에서 k3d image import로 넣은 이미지를 재사용할 때 씀).

⑪

관측성 (Observability) — LGTM 스택

LGTM 스택

Loki(로그) + Grafana(시각화) + Tempo(트레이스) + Mimir(지표)의 앞글자를 딴 이름. 로그·트레이스·지표라는 세 종류의 관측 신호를 각자 전용 저장소에 넣고, Grafana 하나로 다 조회하는 조합이다.

Loki / Promtail

Loki는 로그 전용 저장소 — Elasticsearch와 달리 로그 본문 전체를 색인하지 않고 라벨(서비스명 등) 위주로만 색인해서 훨씬 가볍다. Promtail은 각 노드에서 컨테이너의 stdout을 긁어모아 Loki로 보내주는 수집 에이전트. 코드를 전혀 몰라도 되고, 그냥 화면에 찍히는 텍스트를 그대로 퍼간다.

Grafana

Loki·Tempo·Mimir 같은 여러 데이터소스를 한 화면에서 조회·시각화하는 도구. 임시 조회용 화면인 Explore와, 고정된 패널을 모아둔 Dashboard 두 가지 사용법이 있다.

Tempo / OTLP / span·trace

Tempo는 분산 트레이싱 전용 저장소. span은 "한 서비스가 한 작업을 처리한 구간"(시작~끝 시간 포함) 하나, trace는 여러 서비스에 걸친 span들을 하나로 묶은 것 — "요청 하나가 gateway→order-service→product-service를 거치며 걸린 시간"을 통째로 보여준다. OTLP(OpenTelemetry Protocol)는 이 span 데이터를 전송하는 표준 프로토콜.

OpenTelemetry (OTel) Java agent

애플리케이션 코드를 한 줄도 안 고치고 트레이스를 자동으로 남겨주는 계측 도구. -javaagent:otel-javaagent.jar로 JVM 실행 시 붙여주기만 하면, Spring MVC·RestClient 같은 흔한 호출을 자동으로 가로채 span을 만들고 Tempo로 전송한다.

Mimir / Prometheus / remote_write / scrape

Prometheus는 지표(metric)를 다루는 사실상 업계 표준 — 애플리케이션의 /actuator/prometheus 같은 엔드포인트를 주기적으로 scrape(당겨오기)해서 시계열로 저장한다. Mimir는 이 지표를 대규모로 저장하기 위한 백엔드로, Prometheus와 호환되는 remote_write(밀어넣기) API를 받는다. Prometheus agent 모드는 스크레이프해서 remote_write로 밀어넣기만 하고 자체 조회 기능은 없는 경량 버전이다.

actionId / requestId 상관관계

msa-k3s-lab 랩에서 직접 만든 패턴 — actionId는 사용자의 버튼 클릭 하나에서 시작해 여러 서비스를 거치는 동안 절대 안 바뀌는 값, requestId는 각 서비스가 요청을 받을 때마다 매번 새로 만드는 값. actionId 덕분에 {namespace="default"} |= "그 actionId" 같은 LogQL 한 줄로 여러 서비스에 흩어진 로그를 한 번에 묶어 볼 수 있다. (트레이스의 traceID와 비슷한 발상이지만, 이 랩에서는 둘을 아직 서로 연결하지 않은 별개 체계다.)

⑫

메시징 · 캐싱

Kafka / KRaft

Kafka는 서비스 간에 이벤트(예: "주문이 확정됐다")를 비동기로 주고받는 메시지 큐/스트리밍 플랫폼. 발행자(Producer)는 누가 구독하는지 몰라도 되고, 구독자(Consumer)는 자기 속도대로 처리할 수 있다. KRaft는 Kafka 최신 버전이 쓰는 자체 합의 프로토콜로, 예전에 꼭 필요했던 별도의 ZooKeeper 없이 Kafka 노드들끼리(컨트롤러 쿼럼) 직접 리더를 정한다.

이벤트 발행/구독 (Publisher / Subscriber)

한 서비스(Publisher)가 "이런 일이 있었다"는 이벤트를 큐에 던져두면, 관심 있는 다른 서비스(Subscriber)가 그걸 읽어서 자기 할 일을 한다. 두 서비스가 서로 직접 호출하지 않고 큐를 통해서만 연결되므로 결합도가 낮아진다 — 예: 주문 서비스가 "주문 확정" 이벤트를 발행하면, 재고 서비스가 그걸 구독해 재고를 차감한다.

Redis / Sentinel

Redis는 메모리 기반의 초고속 키-값 저장소로, 세션이나 자주 조회되는 데이터의 캐시로 흔히 쓴다. DB(원장)까지 안 가고 Redis에서 먼저 찾아보는 걸 "캐시 히트", 없어서 DB까지 가는 걸 "캐시 미스"라 부른다. Sentinel은 Redis를 이중화(master + replica)해서, master가 죽으면 replica 중 하나를 자동으로 새 master로 승격시켜주는 HA 구성이다.

이 문서에 없는 용어를 만났다면 — 프로젝트 루트 CLAUDE.md와 각 서비스 디렉토리의 CLAUDE.md에 더 자세한 맥락(왜 그렇게 결정했는지 포함)이 있습니다. 여기 없는 용어를 발견하면 이 문서에 이어서 추가해도 됩니다.
