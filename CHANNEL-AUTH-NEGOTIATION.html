채널 인증 설계 · 협의 자료

슈퍼앱 채널 연동 인증 방식 — 최종 결정과 실행 항목

문서 목적: 채널BFF(AWS)↔뱅킹시스템(IDC) 간 인증 방식 확정 내용을 공유하고, 양측이 각자 준비할 항목을 정리한다.
한 문장 요약 — 세션·토큰을 두지 않고, 채널BFF가 매 요청마다 서명(HMAC)을 만들어 붙이면 뱅킹시스템 게이트웨이가 그 자리에서 검증한다. mTLS(채널 자체 증명)와 서명(요청 단위 증명)이 서로 다른 비밀에 의존해 이중으로 방어한다.
01

배경 — 왜 이 방식에 도달했는가

슈퍼앱 고객은 이미 로그인된 상태로 뱅킹시스템 API를 호출한다. 인증 설계는 세 단계를 거쳐 지금 결론에 도달했다.

시점검토안폐기 사유 / 결과
1차토큰 이중 검증
(gateway가 슈퍼앱 JWKS로 직접 검증)		폐기 뱅킹시스템의 인증 경계가 타사(슈퍼앱)의 서명키·키 교체 일정에 의존하게 됨
2차내부 토큰 교환
(채널BFF가 뱅킹시스템에서 내부 토큰 발급받아 사용)		폐기 "세션(로그인 상태)을 우리 쪽에 유지"하는 전제였는데, 슈퍼앱의 로그인·로그아웃을 감지할 방법이 없다는 게 확인됨 — 세션은 실체 없는 TTL 근사치일 뿐
최종세션 없는 요청 서명
(HMAC, 매 요청 독립 증명)		채택 세션 개념 자체를 버림 — 저장할 것도 폐기할 것도 없음

검토했던 전체 8개 안(교환 대칭/비대칭, BFF 자체서명, 무토큰, opaque+Redis 등)의 상세 비교는 부록(§6) 참고.

02

최종 결정 후보 — v1(HMAC) / v2(mTLS 키 재사용)

둘 다 "세션·토큰을 두지 않고 매 요청을 독립적으로 증명한다"는 방향은 같다. 차이는 서명에 어떤 키를 쓰느냐뿐이다 — 이 문서의 협의 목표는 둘 중 하나를 확정하는 것이다(§5).

v1 HMAC 공유 비밀 (대칭키)

flowchart LR
    BFF["채널BFF
② HMAC 서명 생성"] -->|mTLS| L4["L4"] --> GW["gateway
③ 공유 비밀로 검증"]

양측이 같은 비밀 값을 나눠 갖는다. 구현이 단순한 대신, 비밀 하나가 유출되면 전체 채널이 즉시 위조 가능해진다.

v2 mTLS 인증서 키 재사용 (비대칭키) 권장

flowchart LR
    BFF2["채널BFF
② 인증서 개인키로 서명"] -->|mTLS| L42["L4"] --> GW2["gateway
③ 인증서 공개키로 검증"]

채널BFF가 mTLS 인증서의 개인키로 서명하고, gateway는 공개키만으로 검증한다. 새 비밀이 없어 유출돼도 위조 불가 — IETF 표준(RFC 9421) 기반.

속성v1 (HMAC)v2 (mTLS 키 재사용)
세션/토큰없음 — 저장·폐기·만료 관리 불필요 (양쪽 공통)
gateway가 들고 있는 값위조 가능한 비밀 그 자체공개키뿐 — 유출돼도 위조 불가
새로 만들 것공유 비밀 생성·배포·회전 절차없음 — 기존 mTLS 인증서 수명주기에 얹힘
회전 절차양측 조율 필요(겹침 기간)mTLS 인증서 교체 시 자동으로 같이 됨
구현 난이도낮음중간(비대칭 서명 API 사용)

서명 규격 (양측이 동일하게 구현해야 하는 부분)

서명 대상(payload) = method + "\n" + path + "\n" + timestamp + "\n" + nonce + "\n" + custKey

v1: signature = Base64( HMAC-SHA256(공유비밀, payload) )
v2: signature = Base64( RSA-SHA256_Sign(채널BFF 인증서 개인키, payload) )

전송 헤더 (v1·v2 공통):
  X-Signature : 위에서 계산한 서명 값
  X-Timestamp : 요청 생성 시각 (Unix epoch, 초)
  X-Nonce     : 요청마다 새로 생성하는 난수 (UUID 등)
  X-CustKey   : 슈퍼앱 고객 키값 (1차 검증에서 추출한 값)

이 규격(필드 구성·알고리즘·헤더 이름)과 v1/v2 중 채택안은 협의 확정이 필요한 항목이다 — §5 참고.

03

AWS 측 조치사항

채널BFF(Spring Boot, ECS Fargate)에 서명 생성 로직을 추가하고, 공유 비밀을 안전하게 배포한다.

AWS 채널BFF — 서명 생성 로직 추가

  • 1차 검증 로직은 기존 그대로 유지 — 슈퍼앱 토큰을 슈퍼앱 JWKS 공개키로 검증, custKey 추출
  • 요청마다 HMAC 서명 생성 — 검증 통과 직후, 위 서명 규격대로 계산해 4개 헤더에 실어 전송
  • 서명 계산은 로컬 CPU 연산 — 외부 호출(왕복) 없음

v1 — HMAC (대칭)

@Component
class ChannelRequestSigner(
    private val signingProps: ChannelSigningProperties,  // 공유 비밀 주입
) {
    fun sign(method: String, path: String, custKey: String): SignedRequestHeaders {
        val timestamp = Instant.now().epochSecond.toString()
        val nonce = UUID.randomUUID().toString()
        val payload = listOf(method, path, timestamp, nonce, custKey).joinToString("\n")
        val signature = hmacSha256(signingProps.secret, payload)
        return SignedRequestHeaders(signature, timestamp, nonce, custKey)
    }
}

v2 — mTLS 인증서 개인키 재사용 (비대칭, 권장)

@Component
class ChannelRequestSignerV2(private val mtlsKeyStore: KeyStore) {
    private val privateKey = mtlsKeyStore.getKey("channel-client-cert", password) as PrivateKey

    fun sign(method: String, path: String, custKey: String): SignedRequestHeaders {
        val timestamp = Instant.now().epochSecond.toString()
        val nonce = UUID.randomUUID().toString()
        val payload = listOf(method, path, timestamp, nonce, custKey).joinToString("\n")
        val sig = Signature.getInstance("SHA256withRSA").apply {
            initSign(privateKey); update(payload.toByteArray())
        }
        val signature = Base64.getEncoder().encodeToString(sig.sign())
        return SignedRequestHeaders(signature, timestamp, nonce, custKey)
    }
}

AWS 공유 비밀 배포 — Secrets Manager v1 채택 시에만 필요

v2를 채택하면 이 카드 전체가 필요 없다 — 새 비밀을 안 만들고 기존 mTLS 인증서를 재사용하기 때문이다.

  • 공유 비밀 값 생성 — openssl rand -base64 32 등으로 무작위 값 1개 생성(뱅킹시스템 측과 같은 값 공유 필요)
  • AWS Secrets Manager에 등록 — 별도 설치 없는 AWS 관리형 서비스. 콘솔 또는 CLI로 값만 등록하면 됨
  • ECS 태스크 정의에 연결 — 컨테이너 기동 시 환경변수로 자동 주입(코드에서 SDK 직접 호출 불필요)
  • IAM 역할에 해당 시크릿 ARN에 대한 secretsmanager:GetSecretValue 권한만 최소 부여
## 비밀 생성 및 등록
openssl rand -base64 32
aws secretsmanager create-secret \
  --name channel-hmac-secret \
  --secret-string "<생성된 값>"

## ECS 태스크 정의 — secrets 필드에 연결하면 자동 환경변수 주입
{
  "containerDefinitions": [{
    "secrets": [
      { "name": "CHANNEL_HMAC_SECRET",
        "valueFrom": "arn:aws:secretsmanager:REGION:ACCOUNT:secret:channel-hmac-secret" }
    ]
  }]
}

참고 — 회전(rotation): Secrets Manager의 자동 회전 기능은 한쪽(AWS)만 바꾸면 되는 값(RDS 비밀번호 등)을 위한 것이라, 양쪽이 같은 값을 알아야 하는 이 공유 비밀에는 그대로 못 쓴다. 실제 교체는 겹침 기간을 두는 수동/스크립트 절차다: ① 새 값을 양쪽에 먼저 등록 → ② 뱅킹시스템 게이트웨이가 신·구 값을 잠시 함께 허용 → ③ 채널BFF를 새 값으로 전환 → ④ 구 값 삭제.

AWS 채널 mTLS — 이미 확정된 사항 (참고)

채널BFF는 슈퍼앱 전용 회선(DX)으로 뱅킹시스템 L4에 접속할 때 클라이언트 인증서를 제시해야 한다(mTLS). 이 인증서·개인키의 발급·설치·교체 절차는 별도 mTLS 협의 문서에서 다룬다 — 이 문서는 그 위에 얹히는 요청 서명만 다룬다.

04

뱅킹시스템(IDC) 측 조치사항

게이트웨이에 채널 요청 검증 로직을 추가하고, 같은 공유 비밀을 안전하게 배포한다.

IDC gateway — 서명 검증 로직 추가

  • 요청 종류 분기 — X-Signature 헤더 존재 여부로 직원 요청(JWT)과 채널 요청(서명)을 구분
  • 직원 인증 로직은 기존 그대로 — auth-service 발급 JWT를 공유키로 검증, 변경 없음
  • 채널 검증 3단계 — ① timestamp 유효 창(±60초) 확인 → ② nonce 중복 확인(Redis, 재전송 방지) → ③ 서명 재계산·대조
  • 통과 시 신원을 내부 헤더(X-Account-Id/Roles/X-Principal-Type)로 변환해 하위 서비스로 전달 — 하위 서비스는 서명·JWT를 모른다

v1 — HMAC (대칭)

@Component
class ChannelRequestVerifier(
    private val signingProps: ChannelSigningProperties,
    private val redisTemplate: StringRedisTemplate,   // 재전송 방지 캐시 — 세션 저장 아님
) {
    fun verify(request: ChannelSignedRequest): Boolean {
        val withinWindow = abs(Instant.now().epochSecond - request.timestamp) <= 60
        if (!withinWindow) return false

        val firstSeen = redisTemplate.opsForValue()
            .setIfAbsent("channel-nonce:${request.nonce}", "1", Duration.ofMinutes(5)) ?: false
        if (!firstSeen) return false   // 재전송된 요청

        val payload = listOf(request.method, request.path, request.timestamp,
                              request.nonce, request.custKey).joinToString("\n")
        val expected = hmacSha256(signingProps.secret, payload)
        return MessageDigest.isEqual(expected.toByteArray(), request.signature.toByteArray())
    }
}

v2 — 채널BFF 인증서 공개키로 검증 (비대칭, 권장)

@Component
class ChannelRequestVerifierV2(
    private val trustedClientCert: X509Certificate,   // CA로 이미 관리 중인 채널BFF 인증서
    private val redisTemplate: StringRedisTemplate,
) {
    fun verify(request: ChannelSignedRequest): Boolean {
        val withinWindow = abs(Instant.now().epochSecond - request.timestamp) <= 60
        if (!withinWindow) return false

        val firstSeen = redisTemplate.opsForValue()
            .setIfAbsent("channel-nonce:${request.nonce}", "1", Duration.ofMinutes(5)) ?: false
        if (!firstSeen) return false

        val payload = listOf(request.method, request.path, request.timestamp,
                              request.nonce, request.custKey).joinToString("\n")
        val sig = Signature.getInstance("SHA256withRSA").apply {
            initVerify(trustedClientCert.publicKey); update(payload.toByteArray())
        }
        return sig.verify(Base64.getDecoder().decode(request.signature))
    }
}

IDC 공유 비밀 배포 — k8s Secret v1 채택 시에만 필요

  • AWS와 동일한 값을 k8s Secret으로 등록(신규 테이블·서비스 불필요)
  • Deployment 환경변수로 매핑 — 기존 DB 비밀번호와 같은 주입 방식
  • 비밀값 fallback 금지 — Secret이 없으면 기동 실패(fail-fast)
kubectl create secret generic bank-shared-secret \
  --from-literal=CHANNEL_HMAC_SECRET="<AWS와 동일한 값>" \
  -n bank-dev

IDC 네트워크 격리 — NetworkPolicy

서명 검증은 마지막 방어선이 아니라 두 번째 방어선이다 — 첫 번째는 "이 경로엔 검증된 채널만 도달한다"는 네트워크 격리. gateway의 채널 수신 포트는 Envoy Gateway를 거친 트래픽만 받도록 Calico NetworkPolicy로 강제한다.

apiVersion: projectcalico.org/v3
kind: NetworkPolicy
metadata:
  name: gateway-channel-ingress
  namespace: bank-dev
spec:
  selector: app == 'gateway'
  ingress:
    - action: Allow
      source: { selector: "app == 'envoy-gateway'" }
      destination: { ports: [8443] }

IDC L4 mTLS — 이미 확정된 사항 (참고)

NetScaler MPX 9230에 슈퍼앱 전용 SSL vserver를 신설해 클라이언트 인증서를 요구(mTLS)하는 구성은 이미 지원 확인 완료됐다. 상세 설정 순서(Rewrite 정책 2개 — CN 헤더 삽입/제거)는 mTLS 검토안 문서에서 다룬다.

05

협의가 필요한 항목

이 미팅에서 확정해야 하는 것들이다.

v1 vs v2 최종 채택 — 대칭키(HMAC, 구현 단순)로 시작할지, 처음부터 비대칭키(mTLS 인증서 재사용, 비밀 유출 리스크 원천 차단)로 갈지. 이 문서의 가장 중요한 결정 항목
서명 규격 최종 확정 — §2의 payload 구성(필드 순서·구분자), 헤더 이름(X-Signature 등)을 그대로 쓸지, 양측 프레임워크 제약에 맞게 조정할지
timestamp 허용 오차 — 지금 제안은 ±60초. 두 시스템의 시간 동기화(NTP) 정밀도에 따라 조정 필요
nonce 캐시 TTL — 지금 제안은 5분. 짧을수록 안전하지만 시계 오차 여유가 줄어듦
공유 비밀 최초 교환 방법 v1 채택 시에만 — 누가 생성하고, 어떤 채널로(대면/봉인 전달 등) 상대측에 전달할지 — 평문으로 메일·슬랙 전송 금지
회전 주기와 담당자 v1 채택 시에만 — 몇 개월마다 교체할지, 겹침 기간 동안의 배포 순서와 롤백 절차 담당자. v2 채택 시 이 항목은 mTLS 인증서 교체 절차로 흡수돼 별도 협의가 필요 없다
장애 대응 연락 체계 — 서명 검증 실패가 급증할 경우(시계 오차, 비밀 불일치 등) 상호 연락 창구
06

부록 — 검토했던 전체 안

최종안에 이르기까지 검토·폐기한 안들이다. 협의 중 "왜 다른 방식은 안 되나"라는 질문에 참고한다.

안방식결과사유
1내부 토큰 교환(대칭키, auth-service 발급)폐기세션 전제가 로그아웃 감지 불가로 무너짐
2전용 토큰 서버(비대칭키 신설)폐기동일 — 세션 전제 문제
3채널BFF 자체 서명(발급자=BFF)폐기서명키가 AWS에 상주, 중앙 발급 기록 없음
6무토큰 — mTLS 채널 신원만 신뢰후보가장 단순하지만 감사 추적성이 약함
7HMAC 요청 서명 (세션 없음)채택 기반최종안의 근간 — PKI 불필요, 재전송 방지 내장
8Opaque 토큰 + Redis 세션 조회폐기즉시 폐기는 강점이지만, 애초에 로그아웃을 감지 못해 그 강점을 못 씀
7→v27안을 mTLS 인증서 키 재사용으로 발전최종 후보대칭키 공유 비밀의 유출 리스크를 제거 — 본문 §2 참고

전체 8개 안의 상세 비교(장단점, 소스 구조 스케치)는 별도 레퍼런스 문서에 있다.
